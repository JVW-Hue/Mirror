How we built our cohort modeling pipeline

Posted 2019-11-08 by Elena Vasquez, Principal Engineer

This is a technical post about the architecture behind our Behavioral Modeling practice. If you're not interested in distributed systems, you can skip it. If you are, the rest of this post will make you sad in a familiar way.

The problem

We needed a system that could ingest population-scale event data, de-identify it on arrival, build cohort models on the de-identified stream, and emit predictions back to clients with sub-second latency — all while remaining auditable end-to-end by our Ethics & Oversight Board.

The "auditable end-to-end" requirement is the one that made this hard. Most high-throughput ML systems are not auditable. Most auditable ML systems are not high-throughput. We needed both.

The architecture

We settled on a three-layer architecture:

  1. Ingest: Kafka-based event bus with a de-identification worker at the head. The worker uses a one-way hash of the subject identifier and a rotating salt. The salt rotates every 24 hours and is not stored.
  2. Model: Flink-based stream processor that maintains cohort assignments in memory and emits predictions on subscription. Cohort definitions are versioned and stored in an append-only log.
  3. Audit: Every model decision is logged to a separate, immutable audit store. The audit store is queryable by the Ethics & Oversight Board and is exportable in full to clients on request.

What we learned

The audit layer, not the model layer, is the part of the system that breaks the most often. The model is straightforward to keep running. The audit pipeline is a continuous source of late-night pages.

If you are building a system like this, design for the audit pipeline first. The model is the easy part.

— Elena
